# 旅藏：持续理解旅行需求

打开 `/travel.html`，从对话输入旅行条件。需求摘要用于核对 Agent 记住的内容；已确认条件和暂定条件分别标注。天数与每天可用时间分开保存，预算区分每人／全团、每天／全程。

## 试用一段连续对话

1. “广州三天，我们两个人，每人全程预算1000元，每天最多六小时，必去粤博，不去广州塔。”
2. “预算改为600元。”——沿用此前的每人全程口径，保留天数、同行人和地点条件。
3. “再加上花城广场。”——追加必去条件。
4. “粤博玩两小时够吗？”——回答问题，保留现有行程。
5. 刷新页面，继续修改；点击第1／2／3天查看对应路线和地图。

首次只说“预算1000元”时，Agent 会确认预算口径。首次未给城市或天数时会先问关键条件，每次最多两项。说“先给方案”可以按明确标出的暂定条件起草。使用对话栏的新方案按钮开启另一趟旅行，旧收藏和商家记录继续保留。

条件有冲突时，例如一天一小时却要求必去多处，Agent 解释冲突并要求调整，原方案仍保留。换城市会保留天数、同行人、预算和节奏，清掉旧城市的必去／排除地点。

## 当前数据范围

广州、苏州、杭州目录各有4个地点，有目录来源和预设纪念品。多天安排不重复景点凑满日期，空余时段会明确提示待补充。其他城市由模型提出建议，地点、开放、预约、票价和交通尚未联网核实，无坐标与目录纪念品。

预算是用户的上限，暂未做实际费用核算。转场和游览时间是估算，不包含完整的餐饮、起终点交通或酒店安排。同行人描述不会自动证明人数、年龄或行动能力。

档案和方案保存在当前浏览器的 `lvzang.v1`，最近12条对话单独保存在 `lvzang.chat.v1`。使用同一浏览器、域名和端口；目前没有跨设备同步。失败或停止等待会保留上次已接受的方案和需求。新字段兼容旧版记录，初始广州展示不等于用户确认。

## 后续优先做什么

1. 补充真实地点资料：营业时间、预约方式、门票、停留时间和来源更新时间，再按出行日期校验。
2. 接入地图的实际交通时间，围绕酒店、车站和每日起终点优化顺序。
3. 给路线增加可比较的替代项：用户固定必去地点，比较轻松／省钱／文化方案，并展示改动原因与费用估算。

这些数据和校验能把“符合偏好的行程草案”推进到“可执行的定制旅行”。仅增加提示词不能保证真实票价、预约或交通可行。

## 实现与验证

`travel-profile.js` 负责校验与合并条件，`travel-schedule.js` 负责每日容量和必去约束，`travel-agent.js` 在既有首次对话调用中抽取修订。只改预算、同行人数或开始时间时复用已校验路线，跳过地点推荐调用。带 `profile` 的请求使用新流程，旧 API 请求保持原有行为。模型输出在本地再次校验后才保存；空内容、截断或无效 JSON 在同一阶段最多重试一次，失败时保留旧方案。[DeepSeek JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)只约束 JSON 格式。

运行 `npm test` 检查单元及接口回归；`node tests/travel-understanding.browser.js` 检查连续修改、追问、刷新和每天切换。浏览器检查使用模拟模型响应，不消耗真实额度。
