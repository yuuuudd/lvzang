# 两人分工与阶段交付

默认A=你，B=队友；可根据能力互换，但每个文件应有一位主要负责人。

| 模块 | A：游客体验与3D作品 | B：Agent与商家服务 |
| --- | --- | --- |
| 产品与视觉 | 主导目标用户、界面、美术风格、作品质量 | 评估数据、API与执行边界 |
| 旅行对话 | 聊天UI、处理阶段与修改反馈 | 真实对话、需求提取、上下文、校验 |
| 路线 | 地点故事与画布呈现 | 文化资料、路线组织、条件沿用；交通天气接入排后续 |
| 个人收藏 | 3D展示、个人照片/日期/故事、收藏编辑 | 提供地点关联数据、叙事整理返回 |
| 展览 | 展柜、主题与分享阅读体验 | 内容整理、持久化与分享数据协议 |
| 商家 | 游客定制与报价查看入口 | 商家活动、需求接收、报价和处理状态 |
| 验证 | 游客访谈、桌面移动端体验 | 商家/打印供应方访谈、API与模型行为 |

## 文件负责范围

A主负责：public/travel.html、public/travel-workspace.css、public/src/travel-workspace.js、public/src/travel.js、public/src/souvenir-mesh.js。原照片创作UI/public/src/app.js、trips.js若需要调整，也由A主导。

B主负责：travel-agent.js、server.js、public/src/travel-domain.js、travel-catalog.js、travel-state.js，以及Agent/API相关单测。按需要维护现有agent.js、cloud3d.js、tripo.js等云端创作逻辑，不重写已经工作的流程。

共享协调：package.json/package-lock.json、数据格式、对外接口、PRODUCT.md/DESIGN.md、共用3D导出与创作模块。更改前在对应Issue写明影响与负责人。

目前商家UI也在A负责的travel.js里。B先准备商家数据/服务接口与独立界面模块，由A接入页面；不要两人同时大范围修改travel.js。若确需拆成public/src/travel-merchant.js，先约定接口并由B修改server.js的静态资源白名单，再交给A挂载。

## 分阶段交付

### 第一阶段：各自跑通基础

A：用统一的示例数据跑通地点→个人收藏→展览→分享，输出可在手机使用的完整页面。
B：跑通对话→需求→路线与约束校验，输出可复现输入输出及失败恢复行为。
共同：确定广州同一主题、三个同一地点ID、三件纪念品和同一家示范商家。

### 第二阶段：联调

A：真实显示B返回的回答、阶段、变化和结果；回答问题不重排画布。
B：对话中的时间/预算/必去/排除持续沿用；无来源字段不能标成已核实。
共同：用户加入照片与故事后完成个人展览。此功能当前尚未连成完整流程，不能仅靠已有预制模型宣称完成。

### 第三阶段：商家与交付

A：游客可选择作品并查看清楚的定制单及报价。
B：商家能接收同一订单、记录报价、更新状态；跨设备收单需要后端存储，是新工作，现有localStorage不支持。
共同：接触真实供应方，完成一次报价/打样；若比赛前未完成，明确标为演示或待实施。

### 最后阶段：使用验证与比赛

共同完成真实用户试用、问题修复、三分钟演示、简要商业模式与实际验证记录。每阶段以可运行成果验收，不以页面数量或Agent数量验收。

## 一起验收的完整场景

提出旅行想法 → Agent理解与修订 → 文化体验/照片记忆 → 个人3D收藏 → 展览分享 → 提交可处理的定制单。

必须覆盖：普通问题回答；换城市不沿用广州插画；只改预算保留其他条件；记住必去/排除；失败或取消保留旧结果；手机可用；收藏刷新恢复；分享可读；无付款/到访/实时票价等虚假完成声明。
